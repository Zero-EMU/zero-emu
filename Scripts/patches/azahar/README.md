# FoldArc 对 Azahar 源码的修改

Azahar 以 GPL-2.0-or-later 发布；FoldArc（GPLv3）链接的是打过下面补丁的版本。
`Scripts/build-azahar-ios.sh` 克隆源码后按文件名顺序 `git apply` 这些补丁，已经应用过的会跳过。
每个被改动的源文件里都写明了 "Modified by FoldArc on <日期>"。

| 补丁 | 改了什么 | 为什么 | 影响范围 |
| --- | --- | --- | --- |
| `0001-sw-rasterizer-tile-bands.patch`（2026-10-27） | `renderer_software/sw_rasterizer.cpp` 的 `ProcessTriangle`：小三角形（只占一个 8 行 tile 或包围盒 < 1024 像素）直接在调用线程画；大三角形按 8 行帧缓冲 tile 分成至多 4×线程数 个任务 | 上游每条扫描线排一个任务再等待，剖析显示模拟线程大半时间在工作队列的锁上（`Docs/PERF-SW-RASTERIZER-20261027.md`） | 软件渲染器；输出逐像素不变 |
| `0002-vulkan-ios-simulator.patch`（2026-10-27） | `renderer_vulkan/vk_rasterizer.{h,cpp}`、`vk_instance.cpp`，只在 `TARGET_OS_SIMULATOR` 下生效：①着色器读的 LUT texel buffer 改为设备本地副本，每次上传后 `vkCmdCopyBuffer`；②上传索引时减去最小索引、以 base vertex 0 绘制；③表面不带 storage 用途 | iOS 模拟器的 Metal：①线性纹理只能建在 private 缓冲上；②不支持非零 base vertex；③没有原生纹理原子操作，MoltenVK 把可变格式的 storage 图像建成缓冲背书的纹理，它不能当渲染通道附件，清除时被 Metal API Validation 中止（`Docs/VULKAN-MOLTENVK-20261027.md`） | 仅模拟器构建，设备构建编译不到。③的代价：模拟器里 3DS 阴影贴图（shadow rendering）不可用 |
| `0003-libretro-shader-cache-after-state-load.patch`（2026-10-27） | `citra_libretro/citra_libretro.cpp` 的 `retro_unserialize`：读档成功后像 `do_load_game` 一样重挂磁盘着色器缓存 | 读档会关机再初始化、重建渲染器，Vulkan 管线缓存没有当前磁盘缓存 → 第一次硬件绘制空指针 | 硬件渲染器（Vulkan/OpenGL）的读档 |
| `0004-vulkan-invalid-clears.patch`（2026-10-27） | `renderer_vulkan/renderer_vulkan.cpp`：屏幕纹理加 `eTransferDst` 用途；`renderer_vulkan/vk_texture_runtime.cpp` 的 `ClearTexture`：跳过图像并不存在的层 | ①`FillScreen` 用 `vkCmdClearColorImage` 清屏幕纹理，规范要求 TRANSFER_DST（VUID-vkCmdClearColorImage-image-00002），MoltenVK 也只在有它时给纹理加清除所需的 RenderTarget 用途（读代码发现，测试中未触发）；②不支持分层渲染时立方体表面只有 1 层，但 `RasterizerCache` 启动时清空立方体表面的 6 个面 → Metal API Validation 中止：`Slice is 1, but the texture at attachment 0 has only 1 slices`（模拟器实测，去掉这处即复现） | Vulkan 渲染器；②只在设备不支持分层渲染时起作用 |
| `0005-libretro-reload-and-run-errors.patch`（2026-10-27） | `citra_libretro/citra_libretro.cpp`：`retro_unload_game` 把 `game_loaded` 复位；`retro_run` 里 `RunLoop` 报错时显示消息后返回，不再原地重试 | ①用硬件渲染时 `retro_load_game` 只记路径，游戏在 `context_reset` 里、且仅当 `game_loaded` 为假时才加载；卸载后它仍为真，同一进程里第二次开游戏（退回游戏库再进）根本没加载，之后每次 `RunLoop` 都返回 `ErrorNotInitialized`；②上游的循环遇到这种每次都会出现的错误就永远不返回，`retro_run` 卡死并不停发消息，前端连卸载游戏都做不到（模拟器实测：47 秒约 99 万条 "Fatal Error encountered (1)"） | 硬件渲染器的重复加载；所有 `RunLoop` 报错（出错的那一帧不再出图，下一帧照常重试） |
| `0006-portable-host-paths-in-states.patch`（2026-10-28） | `common/file_util.cpp` 的 `SerializePath`：读档时，路径若仍指向另一个 Azahar 用户目录（`/Azahar/` 后面紧跟 sdmc、nand、sysdata、load 之一），改到当前用户目录下；`core/file_sys/` 里 SD 卡、写入专用 SD、NAND、存档、SD 存档源、系统存档、扩展存档的主机路径和 LayeredFS 的补丁路径，改用 `FileUtil::Path` 序列化（存档里存占位符，和上游的 `IOFile` 一样） | 即时存档里原本存的是这些归档的绝对主机路径。iOS 上 App 的数据容器路径会随更新、重装变化；FoldArc 第十五轮还把用户目录搬进了 Documents。模拟器实测：重装后容器路径变了，读第一次装时存的档，软件就进不了 SD 卡上的文件夹；同一次安装里存、读则正常 | 即时存档与「继续上次」。新存的档不带安装位置；旧档读入时改到当前位置。存档的二进制布局不变（仍是一个字符串） |
| `0007-libretro-mic-drain.patch`（2026-10-28） | `audio_core/libretro_input.cpp` 的 `PollMicrophone`：每帧一直读麦克风，读到前端给不出完整的 128 个样本为止（最多 16 次，2048 个） | 上游每个 `retro_run` 只读一次 128 个样本：60 帧每秒 7680 个，只有打开时 48 kHz 的六分之一，3DS 的麦克风服务收到的数据越来越落后于实际时间。FoldArc 的 `read_mic` 不阻塞，只给这一帧该给的（`FALibretroCore readMic:`），所以读到不满就停 | 只有游戏用麦克风时起作用（`StartSampling` 之后）。前端的 `read_mic` 若是阻塞的，一帧最多多等 16 次读 |
| `0008-z3ds-reader-for-the-frontend.patch`（2026-11-11） | `citra_libretro/citra_libretro.cpp` 末尾加了六个导出函数 `zeroemu_z3ds_open / size / magic / read / close / compress`：用核心自己的 `FileUtil::Z3DSReadIOFile` 按偏移读压缩文件（`.zcci`、`.zcxi`、`.z3dsx`）解压后的内容，用 `FileUtil::CompressZ3DSFile` 压一个文件 | 前端导入时要读文件头里的标题、图标和标题 ID，压缩文件得先解开才读得到；核心链接的 zstd 是静态的、不导出符号，所以从核心里开一个读的口子，前端不用再带一份 zstd。`compress` 只给调试构建的测试用（做一个压缩的测试文件） | 只有前端调用时起作用；核心自己加载游戏的路径没有改 |
